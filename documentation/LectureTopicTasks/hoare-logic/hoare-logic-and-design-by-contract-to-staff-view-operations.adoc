== Overview of Hoare Logic

=== Definition and Form

*Hoare Logic* is a formal method used to reason about the correctness of a program by expressing its behavior using logical assertions. These assertions are called *Hoare triples*. A Hoare triple specifies what must be true before a statement executes and what must be true after the statement executes.

Hoare triples are expressed using the following form:

[.text-center]
*{ P } S { Q }*

Where:

- *P* is the Precondition: condition before execution
- *S* is the Statement: program operation
- *Q* is the Postcondition: condition after execution

This task applies Hoare Logic and Design by Contract to the Staff View side of the Cafeteria Ordering System. The purpose is to formally document what must be true before staff-facing operations run and what must be true after they complete.

=== Partial Correctness and Total Correctness

*Partial Correctness* means that if a program operation terminates, then it produces correct results that satisfy the postcondition, assuming the precondition is true.

*Total Correctness* means that the program operation produces correct results and is guaranteed to terminate.

Total correctness can be expressed as the following:

[.text-center]
*Total Correctness = Partial Correctness + Termination*

== Correctness Analysis

=== Partial Correctness

Each Staff View function is partially correct, meaning that if it terminates, its postcondition holds when the precondition is true.

- `load_staff_orders()` ensures that an authenticated and authorized staff user can load the order dashboard.

- `view_order_details()` ensures that if an existing order is selected, the Staff View displays the correct order details.

- `update_order_status()` ensures that valid status changes for active orders are saved and visible to staff.

- `close_order()` ensures that an active order becomes closed and is no longer treated as active.

- `load_menu_items()` ensures that staff can load the current menu item list.

- `create_menu_item()` ensures that a valid new menu item is created, stored, and visible in the staff menu list.

- `edit_menu_item()` ensures that a valid update to an existing menu item is saved and visible.

=== Total Correctness

The Staff View operations are considered totally correct under the following assumptions:

- Each function performs a finite number of operations.
- Database requests complete within bounded time.
- Backend responses are returned successfully.
- Staff authentication and authorization checks terminate.
- UI refresh or state update operations complete deterministically.
- Invalid input is rejected instead of causing an infinite or undefined state.

== Contract Violations

The following examples show possible Staff View contract violations.

=== Authentication and Authorization Violations

- A user who is not authenticated attempts to load the Staff View.
- A customer account attempts to close an order.
- A non-staff user attempts to add or edit menu items.

Violation example:

----
staff_authenticated = false ⇒ load_staff_orders() is not allowed
----

=== Order Operation Violations

- Staff attempts to view details for an order that does not exist.
- Staff attempts to update an order that is already closed.
- Staff attempts to close an order that is already completed.
- Staff submits an invalid order status.

Violation examples:

----
order_exists = false ⇒ view_order_details() is not allowed
----

----
order_closed = true ⇒ update_order_status() is not allowed
----

----
order_status_valid = false ⇒ status_update_saved = false
----

=== Menu Operation Violations

- Staff attempts to create a menu item with missing required fields.
- Staff attempts to create a duplicate menu item.
- Staff attempts to edit a menu item that does not exist.
- Staff submits an invalid price or empty item name.

Violation examples:

----
menu_item_valid = false ⇒ create_menu_item() is not allowed
----

----
menu_item_exists = false ⇒ edit_menu_item() is not allowed
----

----
menu_item_valid = false ⇒ menu_item_updated = false
----

== Design by Contract and Staff View Correctness

Design by Contract supports Staff View correctness by defining clear responsibilities for each operation.

Each Staff View operation has:

- Preconditions that define when the operation is allowed to run.
- Postconditions that define what must be true after the operation completes.
- Contract violations that describe invalid states or invalid user actions.
- Correctness reasoning that explains why the function produces the expected result.

This helps the team verify staff-facing operations without needing to rely only on informal expectations. For example, the team can clearly state that an order must exist before staff can view it, an order must be active before staff can close it, and a menu item must contain valid data before it can be created.

Design by Contract also improves reliability because it prevents invalid actions from changing the system state. Staff users should not be able to update closed orders, edit nonexistent menu items, or create invalid menu items.
